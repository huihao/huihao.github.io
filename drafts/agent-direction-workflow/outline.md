> 与站内已有文章的分工：���篇《前端岗位的消失论》（2026-11-17）讲**岗位结构**——活儿怎么被重新分配、初级前端怎么办；本篇讲**个人掌控力**——怎么把模型指挥明白、怎么判断它做完了。美团、阿里两条线会重叠，**正文要用不同角度**（那篇用"岗位"，这篇用"验收与上下文"），并在文末互链。

## 0. 选题与主张

- **标题候选**
  1. 指哪到哪：大厂把"驾驭模型"拆成了四件事（推荐）
  2. 模型很强，为什么你反而更忙了
  3. 别再改提示词了：2026 年大厂实践里的四道硬约束
- **一句话主张**：过去两年大家练的是"怎么把话说漂亮"，大厂今年写下来的实践说的是另一件事——**你喂给模型什么、你拿什么判定它做完了、你决定哪一类可以不看**。这三件事才是"掌控力"，而且都可以练。
- **不做的伪对立**（写的时候要躲开）：不要写成"提示词 vs 工作流"的二元对立；不要写成"AI 取代人 vs 人不可替代"。真正的张力是**可核查的**：代码生成速度 → 团队吞吐速度，这两者之间的差值有 Atlassian 和 GitHub 两组独立数据撑着。
- **贯穿全文的证据锚点**：同一件事在四个团队里独立出现同一个答案（Meta / Atlassian / Shopify / Uber），这比任何一家的口径都硬。

## 1. 开篇：两组互相打脸的数据（约 600 字）

- **A 组（GitHub）**：10 月单周 **12 亿+ commit**，比一年前 **+400%**，比 2025 全年还多；今年新建仓库里带 agent 配置文件的仓库 commit 数是**没有的 8 倍**；9 月 **40%+ 的 PR 由 agent 起头**（3 月 17%）。
- **B 组（Atlassian）**：AI 参与 PR 接近 **100%**，**团队吞吐提升卡在约 10%**；Faros AI 研究：团队从低采纳走到高采纳，**PR 在评审队列里多花 441% 的时间**。
- **要问的问题**：同一批模型，为什么有人提速有人更忙？答案不在提示词里。
- **落点句**：写代码这块板子已经被人踩平了，塌陷的是板子周围的东西。

> 写法提示：两组数据都出自官方博客，**必须标口径**（"GitHub 官方 Octoverse" / "Atlassian 引用 DX 纵向数据"）。不引"AI 很厉害"的空话。

## 2. 第一节｜人的位置：从"环里"挪到"环上"（约 1100 字）

- **论点**：大厂给出的第一个共同动作不是换工具，是**换站位**。人不再逐步骤执行，而是定目标、看运行、跑偏时介入、最后签字。
- **素材**
  - Meta M1：**human-in-the-loop vs human-on-the-loop** 的对照定义；人的工作从"执行步骤"变成"拥有结果、守住质量线"；并且 Meta 明确说这是目标而非已完成状态（有的阶段仍要人盯每一轮）。
  - 阿里 C6：**人在 loop 之内 vs 人在 loop 之上**——人和 agent 都困在环里，改善都有限。
  - 阿里 C3：Anthropic 对约 **40 万次 Claude Code 交互式会话**的分析：**人承担约 70% 的规划决策，agent 承担约 80% 的执行决策**。
  - Shopify S1：**两人一个 pod**，每人同时指挥多个 agent，人管的是"这个 pod 的产品区"而不是"这一行代码"。
  - Anthropic N1：自上而下的自动化会**诱发专家抵制**（"能审双倍案例，怎么激励他审双倍？" → agent 被搁置）；自下而上的个人玩法又有维护黑洞。
- **表 1｜环里 / 环上的分工对照**（3 列 × 6 行左右）
  - 列：环节 / 环里（human-in-the-loop）做法 / 环上（human-on-the-loop）做法
  - 行：定目标、拆任务、写实现、验证、评审、放行上线
  - 底部一句：环上不是不管，是**管的东西换了**——从"每一步怎么做"换成"什么算完成、什么时候必须停"。
- **落点句**：你现在的用法，大概率还是环里。

## 3. 第二节｜上下文不是越多越好，它有权威等级（约 1200 字）

- **论点**：大厂都在做同一件事——**只把"该被听见的"放进模型耳朵里**，并且给每类信息标清楚"谁说了算、什么时候算数"。这是"指哪到哪"的物理基础。
- **素材**
  - Anthropic（转译线索 C3/P3，正文引观点不引数字）：上下文工程 = 维护**最小有效高信噪比 token 集**；just-in-time 检索替代全量灌入；提示词要"合适高度"；工具少而精比多而全好。
  - Google G1 **Agent Distraction**（本节最硬的数字）：13% 会话被 TODO 注释干扰；6% 触发二次动作，其中 **83% 人根本没要求**；**41% 去追已关闭的死单、57% 越界扩范围**；代价是单会话**多 70% 步数、多 77% token、多 105% 等待时间**。→ **你仓库里那些"过时但还在的东西"，正在偷偷给 agent 派活**。
  - 美团 C1：AI 误报三大类——**代码可达 ≠ 运维可达**；把有意为之当缺陷；**AI 给的修复建议本身也要审**。解法不是更多文档，是**显式的不变式**，并且和代码放一起维护；喂过时文档会把 AI 带偏。
  - 阿里 C3：上下文资产五类（Skill/MCP/SPEC/README-runbook/模板-checklist）；"决定 agent 能不能稳定工作的，不是单次 prompt 写得好不好，而是组织有没有把高质量上下文沉淀成可复用资产"。
  - 阿里 C6：高德四层知识（代码 → 工程术语 → 业务知识 → **质量门禁与常见问题**）；通用领域 one-shot 成功率可达 90%，专业领域明显下降。
  - Anthropic N3：skill 与指令**要评测**（Google G7 引用：SkillsBench / SWE-Skills-Bench 上 307 个确认的 skill 诱发失败）；"更长的指令文件会降低遵从度"。
- **表 2｜上下文的来源与权威等级**（4–5 列）
  - 列：来源（架构与不变量 / 规范与门禁 / 当前任务的规格 / 历史与事故 / 仓库现状）· 谁负责维护 · 什么时候进上下文 · 过期了会怎样 · 该不该给 agent 看
- **落点句**：给模型上下文像给新人做入职材料——**给错版本比不给更糟**。

## 4. 第三节｜"做完了"必须落在证据上（约 1300 字，全文重心）

- **论点**：几乎每一家都在同一处踩坑——**模型说做好了**。大厂给出的解法高度一致：**把完成定义成一条可执行的检查，而不是一次自我报告**。
- **素材**
  - Meta M1：门槛设在 **verification 而不是 compilation**——自动测试 + UI 视觉检查都过才算完成；agent 先自检再交给人，所以人看到的是"更少但更可信"的一批；**弱信号不解除约束，只是把约束从写代码挪到读代码**。
  - Uber U1：**确定性交给确定性工具**（布尔代数/条件简化走 PolyglotPiranha），agent 只接需要判断的；**CI 是唯一真相源**；每个 fixer **权限收窄**（测试 fixer 只能改测试文件，否则 agent 会改生产代码让失败测试变绿）；**CodeCourt 把约束拆成一条属性一个 reviewer agent，并行跑，全过才给人看**。
  - 美团 C1 **四层证据表**（静态推理 / 构建+单测 / 集成测试 / 运行时日志）与硬数据：117 个疑似问题 → **36 条红测试确认、3 条被证伪、41 条源码确认、37 条未验证**；11 天 67.8 万行日志 → **5 个缺陷全属实、零误报**；并列出每层"回答不了什么"。
  - Google G4 **Sashiko**（本节最硬的一组对照数据）：干净通过 vs 带警告通过，**60 天返修率 0.9% vs 7.6%**；内核 60 天返修率 **3.4% → 2.2%**；并引 Google 自己的结论：**coding agent 不擅长审自己的代码**。
  - Google G2：**行为评估**像集成测试（提示欠明确会不会先澄清、改构建文件前会不会跑 validator）；G3：**更多 eval 不等于更多修复**，质量来自按 eval 结果动手。
  - Anthropic N2：多 agent 里"单 agent 端到端审"不如"聚焦子 agent 各审一条"（与 Uber CodeCourt 同构，互相印证）。
  - 美团 C1 反面：**多 agent 投票 ≠ 正确性**（盲区共享，票数是重合度）。
- **表 3｜证据的四个层级**（4 列 × 4 行）
  - 列：证据层 / 能回答什么 / 回答不了什么 / 谁能生产
- **落点句**：验收不是"检查一下"，是**先把"完成"写成一条会变红的检查**。

## 5. 第四节｜人管的不是每一步，是"哪一类可以不看"（约 1000 字）

- **论点**：人肉盯每一行不现实也不必要。大厂的做法是**按风险分级授权**：低风险交给机器并事后审计，高风险永远留给人签字。
- **素材**
  - Runway B2（厂商自报，口径要标）：风险分级审批；AI 单独批准的 PR **回滚率 0.10%**，人批约 1/200；9–10 月 AI 批的 977 个 PR 人反对 **1.5%**；中位首审等待 **2.3h → 5min**。同文给出**工程师的新职责四件事**：找 agent 在哪儿浪费力气、清阻塞、把路径改造成 agent-friendly、**保持度量诚实**。
  - Zalando B1：**33% PR 判低风险自动批准，lead time −20~40%**；规则由生产事故倒推；副作用：工程师会主动把改动拆小。
  - Shopify S1：**agent 当第一评审**（对抗性评审在人类之前）；每天汇总评审意见回写 skills 与 Architecture.md → **一次评论变成此后每个 PR 的规则**。
  - OpenAI O3：权限靠 profile + 沙箱 + 分层配置，不靠"提醒模型记得遵守"。
  - 美团 C1：分层授权（只读分析 → 受控修改 → 受控执行 → 人工决策）；**AI Debug 只能当假设生成器，根因认定必须由人做**。
  - 阿里 C2：人要先设定**目标、质量、权限、停止条件**四类边界。
- **表 4｜风险分级与人的介入点**（3 列 × 4 行：低风险 / 中风险 / 高风险 × 自动范围 / 人必须做的 / 事后审计）
- **落点句**：真正省时间的不是让 agent 多写，而是**让你不必看**。

## 6. 第五节｜把它变成你自己的工作流（约 1200 字，全文最"能用"的一节）

- **论点**：上面四节是共识，这一节是**动作**：一个人、一个仓库，今天就能开始做的五件事。
- **五个动作（每条配 1 个大厂出处 + 1 句可执行指令）**
  1. **把"完成"写成一条会红的检查**（Meta M1 验证门槛 + 美团 C1 红测试）——任务描述里写死验收命令、必须覆盖的边界、禁止事项；不要写"优化一下"。
  2. **把不变量和门禁写成文件，和代码放一起**（美团 C1 + 阿里 C6）——每次评审暴露的"上下文缺失"，补的是**那条缺失的规则**，不是往 AGENTS.md 里堆结论。
  3. **让 agent 先自检，再交给你**（Meta M1 + Uber U1 CodeCourt）——每类改动配一个只检查一条属性的评审 agent；**别让它自己审自己**（Google G4 同证）。
  4. **把大任务拆成小检查点**（Shopify S1 + GitHub H2 stacked PR）——PR 是小检查点不是整屏；能并行的拆并行（Shopify pod、OpenAI Pando 4 个 agent 并行、Asana 4 个并行 + 每天查两次）。
  5. **给评审换一个干净的上下文**（Anthropic N2 + Uber U1）——评审 agent 不复用实现 agent 的记忆，只给它规格 + 真实 diff。
- **状态交接怎么办**（长任务）：状态存在上下文之外（OpenAI O1：task service / dispatch loop / 订阅唤醒；Anthropic N3 记忆分层；阿里 C3 上下文资产）——一句话原则：**任务状态写在文件里，不靠模型记着**。
- **反模式清单（建议做成卡片式小节，6–8 条）**
  - one-shot 让模型重写整个模块（Shopify S1 明说）
  - 把整个仓库塞进上下文（G1：多 77% token）
  - 让写代码的 agent 自己审自己的代码（G4）
  - 拿多 agent 投票当正确性（C1）
  - 允许 agent 改测试来让它变绿（U1）
  - 只在"改完时"检查 spec 与代码是否一致（P2：spec 会腐化）
  - 拿模型自述当交付证据（C1："流畅不是证据"）
  - 只跑 eval 不按 eval 结果改（G3）
- **落点句**：掌控力就是**让模型没法糊弄你**。

## 7. 第六节｜岗位和人去了哪里（单独成节，约 1100 字）

- **论点**：这套流程改的不只是任务，还有**人的分工**。要分清两件事：**岗位消失**和**人消失**不是一回事。
- **素材（Anthropic N1 是本节主干）**
  - **只有 2 家**因 AI 自动化彻底消灭一个岗位并让人失业；**10 家**因 AI 增加招聘；但 **2/3 的公司因 AI 减少招聘**（"我们可能不裁人，但我们不招人"），1/3 是自然减员不回补；**9 家砍掉外包**（多已离岸）；价值多数来自"增加产出"而非"削减成本"。
  - 编码提速后，**评审、销售、战略决策**成为新瓶颈（"其他环节得跟上"）。
  - **初级律师的新工作法**：AI 写初稿后，初级律师不再写初稿，改为必须和资深律师一起逐句改 AI 初稿——"如果不写，初级律师怎么知道这是好草稿还是坏草稿？"（判断力从"写"迁移到"看"）。
  - 岗位**被拓宽**：一个人端到端负责一条工作流；人被 redeploy 到 AI 做不了的瓶颈任务。
  - 组织侧信号：阿里 C2 的"留白/沙箱"、Agentic SOC 把产品研发安全并成一个团队、需求周期 50.9 → 13.8 天；Shopify S1 的 pod；OpenAI O8 Revolut "下放执行权、不下放责任"。
  - 非技术者受益：会计师把 80 小时审计做成应用、机场运营、化工厂 QA——**但自建工具的维护成本会吃掉收益**（N1：SaaS 30 美元 vs 维护成本）。
- **必须写清楚的三层区分**
  1. **岗位名还在**（产品、评审、测试、知识工程都还在）；
  2. **活儿换了承接人**（起草从人转到模型，判断留在人手里）；
  3. **人真的被替代**——目前公开可查的极少（2 家），但**"不招人"正在大规模发生**（2/3），这是没有通知、没有补偿、也无处申诉的那种消失。
- **三类人的具体处境**（各 1 段，不要写成建议清单）
  - 还在学校/刚入行：职业阶梯第一级被抽走，最先被影响的是"先写再被改"这条路；
  - 中层：编制没变，单位时间要求的产出变多，"省下来的时间"默认被填进下一个需求；
  - 负责人：真正的新工作是**重新定义什么算完成**，这是权力也是责任。
- **落点句**：这套流程对已经在场的人是升级，对正准备进场的人是关门——因为入门那级台阶（写初稿）正在被抽走。

## 8. 收尾：把问题换成一个可回答的（约 400 字）

- 回到开篇：模型很强而你更忙，不是模型的问题，是**验收和上下文没跟上**。
- 掌控力可以拆成四件可练的事：**给什么、怎么算完成、哪类不用看、状态放哪**。
- 结尾给一个今天就能做的动作：**挑你手上一个真实的待办，用"验收命令 + 禁止事项 + 证据要求"重写一遍任务描述，交给 agent 跑一轮，然后看它交回来的证据够不够你签字。**
- 可选收尾引语：Meta "agents need a way to discover when they are wrong" / 美团 "流畅不是证据，一致不是正确，变绿不是解决" / Shopify "A document explains why the rule exists; CI decides whether the rule was followed"。三选一，别都塞。

## 写作纪律（照着上一篇的教训执行）

1. **不要伪对立**：不写"提示词 vs 工作流""取代 vs 不可取代"。真张力只有"生成速度 vs 团队吞吐"这一条，且有 Atlassian + GitHub 两组独立数据。
2. **不写思考过程**：正文里不出现"我先查了资料""下面分三部分"这类叙述；结论和取舍理由写进去，查资料的过程不写。
3. **第一人称口语**，段落长短打散，并列小节不等长；不要每段都收金句。
4. **数据必须带口径**：厂商自报就写"官方博客披露"，内部测量就写"内部测量"；论文就写"论文"。
5. **必须区分岗位消失 vs 人消失**，且人的去向单独成节（§7），不混在别的节里带过。
6. **每节最多 3–4 个数字**，其余进附录表；一节堆 8 个数字等于一个都没记住。
7. **表格控制在 4–6 行**，宽表在公众号渠道会崩（站内可以，公众号转竖排卡片）。
