这两年自托管的 AI 工具大多是"一个人的聊天框"加一层 RAG：本地跑个模型，传几份 PDF，问它几个问题。

[Octop](https://octop.cloud/)（腾讯云，`TencentCloud/Octop`）想解决的是另一个问题：**家里或小团队只有一台机器，怎么让多个人各自拥有一个助手，而彼此的记忆、文件、权限不串台。**

它给自己的定义是"A smarter, self-hosted AI assistant — multi-user, multi-agent"，README 里写着"It's not just a tool — it's a digital life form that can operate in parallel"。官网首页的说法更具体：**"一台机器跑一套服务，家人和同事各有一个只记得自己事情的助手，换角色不用换环境。"**

这句话是理解 Octop 的钥匙。它的竞争维度不是"我的 Agent 会不会写代码"，而是"一个实例能不能变成一屋子同事"。

本文基于 Octop 的公开文档、README 与更新日志做拆解，先说清它是什么，再讲我认为最值得抄的七个设计，最后对照同类工具说明它强在哪、弱在哪。

## 一、Octop 是什么

MIT 许可，Python 3.12+，`FastAPI + uvicorn` 后端配 `React + TypeScript + Vite + Ant Design` 前端，定时任务交给 APScheduler。官网标注 12100+ Star。

五个零件构成了它的全部：

| 零件 | 干什么 |
| --- | --- |
| **专家**（Expert） | 你的数字同事。一个专家一份工作，各自的文件、模型、聊天记录、记忆 |
| **模型** | 专家思考用的服务。OpenAI 兼容 / Anthropic / DashScope / Ollama 等任意端点，可池化 + 自动路由 |
| **知识库** | 放 PDF、Word、表格。回答会列出用了哪几段原文 |
| **连接器**（Connector） | 专家能操作的应用。腾讯文档、会议、Notion、企查查……授权一次即可 |
| **通道**（Channel） | 从微信、飞书、钉钉等地方够到它的入口 |

架构上最值得记的一点：**一个进程搞定所有入口。** `octop run` 同时起 Web 面板、IM 通道和定时任务，全部走同一个进程内的 HarnessProcessor；重启后状态从控制面库重建。控制面用 SQLite（WAL）或 PostgreSQL，工作区后端另行插拔。

## 二、最有用的七个设计

### 1. 多人共用一台机器，但谁也看不见谁的事

Octop 的多用户不是"共享空间"，而是**各自有工位**：

- 一个实例可以有多账号，JWT 隔离；管理员能按用户组、按页面 Tab 授权——技能包、知识库、连接器、模型、存储、专家可以逐项开放。
- 专家是隔离单元：各自的工作区文件、模型、聊天历史、记忆互不相干。
- 专家可以开 **Share with other users**：别人能跟你同一个正在跑的专家对话，但只有你能改它的设置和文件。
- 知识库可以共享**只读**；连接器实例可以共享使用，配置仍然只有所有者能改。

对照 Open WebUI 的多用户（更像"一个共享空间"）和 Dify 的多用户（其实是"发布应用给不同用户用"），Octop 的模型更接近现实里的团队：同事能用你写的专家，但不能改你的专家。

### 2. 专家是岗位，不是会话

一个专家对应一份**相对稳定的工作**——周报、调研、代码审查，而不是一次性的聊天窗口。配置上，专家有三种默认对话方式：

- **Ask**：只读，读文件、搜网页；
- **Plan**：把计划写进工作区；
- **Craft**：动工具、技能和连接器。

再往上是人格：16 种 MBTI 人格加一个互动测评，决定它的语气和推理风格。`Discover Experts` 里随安装包提供 22 个专家模板，业务流程、知识工作等场景开箱可用。子 Agent 也在这里：专家可以在对话里 `@` 另一个正在跑的专家，或用 `ask_agent` 另开线程。

再进一步是**专家团队**（Beta）：一个主持人专家负责分派，成员各自回话，答复都留在同一条时间线上。限制写得很清楚——成员必须是本地普通专家、团队不能再套团队、通道只绑主持人。

2026-11-15 的 1.0.3b6 还加了**托管专家**：把整段对话交给后端 Agent（比如 OpenCode）去跑。一个敢承认"这活我不干，交给别人"的产品，比什么都自己硬扛的诚实。

### 3. 它住进你已经在用的 IM

支持飞书、企微、钉钉、QQ、微信、Telegram、Discord，扫码即可绑定。通道的职责非常克制：**只负责把消息送进来、把回复送出去**。

一旦绑定，"每天几点把昨天的会议纪要发到群里"这类事就不需要你打开任何界面——定时任务（cron）和主动关怀推送会替你送到微信或飞书。语音输入输出也在（腾讯云边说边出字）。

这是 Octop 与"网页聊天框"最实际的差别：**Dify 和 Open WebUI 是你打开网页才用得上；Octop 是你在微信里就能用。**

### 4. 它真的会用你的电脑

这一层的完整度超出同类：

- **浏览器工作台**：真实 Chromium over CDP，持久化 profile（登录态留在磁盘），每个用户一个独立 profile，空闲 30 分钟自动回收（`OCTOP_BROWSER_IDLE_TIMEOUT_MINUTES`）。Agent 驱动浏览器时，你可以**随时接管同一个会话**，你的点击和输入会顶上去，直到你交还控制权。
- **终端 AI+**：浏览器里开多个交互式 shell 标签页；它和聊天 Dock 里的终端共享同一会话，命令和输出不会两边打架。
- **远程桌面**：在浏览器里看并操作宿主机桌面，可调分辨率与帧率、可用快捷键、全屏。最多 **3 人**同时连接。macOS 需要给运行 Octop 的程序授 Screen Recording 与 Accessibility；Linux 没有图形会话时可以装虚拟桌面。
- **远程手机**（实验）：看并操作 USB 连接的安卓设备或安卓容器。

配套的安全中心有六个页签：工具审批、文件访问、敏感信息脱敏、命令护栏（allow / deny 规则）、技能扫描、审计日志。最高风险的四类工具 `bash`、`execute`、`write_file`、`edit_file` 默认就在审批名单里，但**"手动工具审批"的总开关默认是关的**——需要你自己打开（后面讲短板会再提这点）。

### 5. 连接器：把"你的应用"变成专家的手

内置清单长得像一份腾讯生态 + 通用 SaaS 的混合目录：

- **办公**：腾讯文档、腾讯会议、腾讯乐享、腾讯微云、腾讯 ima、飞书 CLI、企微 CLI、钉钉 CLI、Agent Mail；
- **笔记知识**：有道云笔记、Notion、语雀、Obsidian、OpenAlex、WeKnora、RAGFlow；
- **出行**：飞猪、百度地图、美团、滴滴；
- **邮件任务**：个人邮箱（QQ 邮箱、网易、Gmail 等，IMAP/SMTP）、TickTick；
- **资讯**：腾讯新闻、微信读书、QQ 音乐；
- **专业**：企查查（元典）、Dify（走它的 MCP Server URL）。

授权方式是"扫个码 / 点一下授权 / 粘个 key"，然后**Probe** 探活，token 存在 `~/.octop/secrets/`。之后你不用记工具名，直接说"看看明天我的会议"或"把这些笔记写进腾讯文档"。

内置清单不够用时，可以注册任意 MCP server（HTTP 或 stdio），支持 OAuth：Octop 能通过 401 与 RFC 9728 发现授权服务器，也能手工填 Client ID / Secret，回调地址是 `<public base>/api/connectors/oauth/callback`。更彻底的做法是把插件、专家、技能市场都自建到内网——官方文档给了私有市场的 HTTP API 规范。

### 6. 双向协议：既能收编 coding CLI，也能被别的 Agent 调用

这是 Octop 架构上最有野心的一处。

**向外（ACP）：**

- `octop acp` 把自己的专家暴露给 IDE 和终端。
- 反过来，它内置的 `acp_runner` 工具可以把编码子任务**委派**给外部 CLI：OpenCode、Claude Code、Codex、Cursor CLI、Kimi Code、CodeBuddy、Pi，共七个内置 runner，也支持自定义。权限请求会就地出现在对话里，你可以自己点，也可以让 Agent 用 `action=respond` 代答。

```text
action=list | start | message | respond | status | close
```

**向外（MCP）：** `/api/mcp/agents` 是一个 Streamable HTTP 端点，别的 MCP 客户端可以直接调用你装好的专家：

| 工具 | 作用 |
| --- | --- |
| `list_octop_experts` | 列出你能看到的专家 |
| `call_octop_expert` | 开一段隔离对话，返回 `thread_id` 可续 |
| `resume_octop_expert` | 继续一段卡在审批或提问上的调用 |

访问令牌默认 24 小时有效。

两条方向合起来看，Octop 想当的不是"又一个 harness"，而是**Agent 之间的路由层**：既能把 coding CLI 收编进来当打手，也能把自己的专家端出去被别人调用。Claude Code、Codex、OpenCode 都不占这个位置。

### 7. 数据留在自己机器，后端还能换

- `~/.octop/` 下是全部家当：数据库、工作区、secrets、日志、插件。
- **工作区后端可插拔**：本地磁盘、Docker 沙箱、OpenSandbox、PostgreSQL、COS / S3、火山引擎 TOS。沙箱作用域可以是"每专家一个""每用户一个""固定一个"。1.0.3b6 起管理员可以限制用户建专家时能选哪些后端。
- **记忆可移植**，随工作区一起迁移。`Personalization → Memory` 里可以手改"用户档案"和"强记忆"；新记忆和旧记忆打架时它会**先问你**再写，不会悄悄覆盖；压缩记忆时聊天区会显示进度并暂停发送。
- **知识库**可以完全本地索引：本地 ONNX（中文推荐 `BAAI/bge-small-zh-v1.5`）或在线嵌入；扫描件和图片走 OCR（本地 RapidOCR 或在线视觉模型）；1.0.3b5 加了 rerank，1.0.3b6 加了知识图谱。
- **多实例**共用一个 PostgreSQL 即可共享定时任务、频道、插件和已发布专家（1.0.3b3 起），1.0.3b6 补上了 Helm chart。
- 运维细节也到位：TOTP 与 Passkey、LDAP 账号登录、完整备份与恢复、`octop update` 只换 wheel 不动数据。

## 三、和同类比，强在哪

先摆一张形状对照表（信息截至 2026 年 11 月，依据各项目公开文档）：

| 项目 | 定位 | 部署 | 多用户与权限 | IM 通道 | 操作真实电脑 | 协议位置 | 许可 |
| --- | --- | --- | :-: | :-: | :-: | --- | --- |
| Claude Code | 编码 harness | 终端 / 桌面 / Web | 单用户 | ❌ | ❌ | 客户端 | 闭源 |
| Codex CLI | 编码 harness | 本地 + 云端任务 | 单用户 | ❌ | ❌ | 客户端 | Apache-2.0 |
| Open WebUI | 自托管 AI 家 | 私有部署 | 有，共享空间 | ❌ | 终端扩展 + Computer（生态项目） | 客户端 | 需保留品牌 |
| Dify | LLM 应用开发平台 | 私有部署 / 云 | 应用发布维度 | ❌ | Agent 沙箱 | 服务端 API | Apache-2.0 + 附加条件 |
| **Octop** | **自托管 AI 同事平台** | **私有部署 / Helm** | **多用户 + 分组授权 + 专家共享** | **✅ 飞书/微信/钉钉/QQ/TG/Discord** | **✅ 浏览器 / 终端 / 远程桌面** | **ACP 双向 + Agent MCP** | **MIT** |

三条真正成立的差异：

**第一，它的竞争维度是"协作"，不是"能力"。** 别人比的是"我的 Agent 会不会写代码"，Octop 比的是"这个实例能不能变成一屋子各有分工的同事"。多租户隔离、专家共享、分组授权是产品级的设计，不是加个登录页能补上的。

**第二，入口生态和连接器生态它都做了。** IM 通道（飞书、微信、钉钉…）加上一整套连接器清单（腾讯文档、Notion、语雀、企查查…），落在同一个产品里。别人要么只有前端（Open WebUI），要么只有工作流引擎（Dify），要么只有终端 harness（Claude Code、Codex）。

**第三，协议上它抢的是"中间层"位置。** 一边通过 ACP 把 coding CLI 收编成子任务执行者，一边通过 Agent MCP 把自己的专家暴露给外部 Agent 调用。1.0.3b6 的"托管专家"更进一步：整段对话交给 OpenCode 这类后端 Agent。这条路线目前几乎没有别人在做。

顺带说一句许可：Dify 用的是 Apache 2.0 加附加条件的 Dify Open Source License，Open WebUI 要求保留品牌，**Octop 是纯 MIT**。再配上可插拔的存储后端与自建市场能力，它的可控性在同类里是领先的。

## 四、得说清楚的短板

**版本还在 beta 轨道上。** 更新日志已经到 `1.0.3b6`（2026-11-15），而 PyPI 上的稳定版还是 `1.0.2`（2026-10-18）。PyPI 累计 68 个版本说明迭代极快，也说明接口会变——写自动化脚本要留出余量。

**默认安全偏松。** "手动工具审批"总开关默认关闭，高风险工具虽然默认在名单里，但整体闸门要自己打开；1.0.3b6 才补上"不能再把宿主机目录挂进 Docker 专家"。给生产环境开 shell 之前，命令护栏和文件访问规则一定要自己收紧。

**几处硬限制。** 远程桌面最多 3 人同时连；浏览器要额外装 `browser` extra，Docker 镜像也不带 Playwright Chromium；部分连接器（飞书 CLI、企微 CLI、钉钉 CLI）要求宿主机先装对应命令。

**Beta 与实验标签不少。** 专家团队、云端协同、知识库页面都标着 BETA，远程手机标实验。功能是真的，但接口和体验仍在改。

**运维门槛。** 单机一键脚本很顺，但 LDAP、多实例共享 PostgreSQL、Helm 部署是运维活；而且它是 Python 3.12+ 起的完整服务，不是能塞进任何角落的小工具。

**站点与命名的小坑。** 官网导航里的"扩展"页目前是 404。另外注意辨析：**PyPI 上的 `octop` 才是这个项目**；npm 上同名的 `octop` 是另一个包（一个 GitHub API 封装）。

## 五、适合谁，不适合谁

**适合：**

- 家里或小团队想"一人一个助手"，又不愿意把聊天记录交出去的人；
- 已经在飞书 / 微信 / 钉钉里办公，想让助手住进日常沟通的人；
- 需要它真的动手操作自己的电脑（浏览器、终端、桌面），同时要求动作可审计的人；
- 愿意自己扛一台机器的人：家用服务器、NAS、飞牛、VPS 都行。

**不适合：**

- 只想要一个网页聊天框的人；
- 只写代码、不需要多人也不需要 IM 的人——Claude Code 或 Codex 更利；
- 想编排企业工作流、要 LLMOps 观测面板的团队——那是 Dify 的路；
- 需要商业版、SLA 与厂商支持的人——Octop 目前没有商业版。

## 六、上手路径

1. **装**：一行脚本 `curl -fsSL https://download.octop.cloud/octop/scripts/install.sh | bash`（Windows 用 `install.ps1` / `install.bat`），或 `pip install octop`，或 Docker Compose，或 Helm。
2. **初始化**：`octop init` 建库、生成 JWT、创建第一个管理员；`octop run` 前台跑（默认 `127.0.0.1:8088`）；`octop service start` 注册为系统服务。
3. **配专家**：`Discover Experts` 里挑模板或自建，设定 Ask / Plan / Craft，绑模型（本地 Ollama 也行）。
4. **灌知识**：上传文档，开本地 ONNX 索引，中文推荐 `BAAI/bge-small-zh-v1.5`；要读扫描件再开 OCR。
5. **接应用**：连接器里授权你要用的服务；自定义 MCP 可以挂 OAuth；token 都在 `~/.octop/secrets/`。
6. **接入口**：通道里扫码连飞书、钉钉、企微或 QQ；再加一个定时任务做每日推送。
7. **让它动手**：装 `browser` extra 打开工作台浏览器；远程桌面需要给运行 Octop 的程序授录屏与辅助功能权限。
8. **记得备份**：`octop backup`，换机器前尤其要做。

## 结语

Octop 的贡献不是把聊天框做得更花哨，而是把**"一个助手服务一家人"**这件事做成了产品：一个人建实例，一屋子人各领一个专家，各自带记忆、各自带文件、各自接上自己用的 IM，谁也看不见谁的事。

在这个前提下，它那些看起来很"工程"的设计才站得住脚：ACP 与 Agent MCP 双向、MCP 连接器的 OAuth 发现、可插拔的存储后端、本地 ONNX 索引、六页签安全中心。它们解决的不是"AI 能不能干活"，而是**"一屋子 AI 同事一起干活时，谁的活、谁的权限、谁的锅"**。

如果你家里或团队里正好有一台闲着的机器，Octop 值得花半小时装上试试；如果你只是想找个顺手的代码助手，它大概率是绕了远路。
