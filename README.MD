# huihao.github.io

My blog — a [Jekyll](https://jekyllrb.com/) site published through GitHub Pages.

The look follows the Apple Human Interface Guidelines: the system font stack,
the iOS system colours in both a light and a dark appearance, translucent
materials, generous corner radii and the spring easing that native apps use.

## Layout

| Path | What it is |
| --- | --- |
| `_posts/` | the blog posts |
| `_layouts/`, `_includes/` | Jekyll templates |
| `index.html`, `article/`, `about.md` | the pages: the list, the categories, the tags, the archive and the about page |
| `search.html` | the search page, the index comes from `pagefind/` |
| `404.html` | the page GitHub Pages serves for a missing address |
| `feed.xml` | the RSS 2.0 feed, `/feed.xml` |
| `src/sass/` | Sass sources — `_tokens.scss` holds the design tokens |
| `src/img/` | the images the site uses, `app-icon.svg` and `og-default.svg` included |
| `src/js/` | the browser scripts: `site.js` (reading progress, copy buttons, reading time, appearance) and `search.js` |
| `dist/css/`, `dist/img/`, `dist/js/` | build output, committed because GitHub Pages serves the site as plain static files |
| `pagefind/` | the search index, committed for the same reason |

## Writing

Every post carries a `description` in its front matter. It is the summary the
list card shows and the description the search engines and the social cards
read, so a post should have one:

```yaml
---
layout: post
title: "vue项目如何进行单元测试"
description: 用 Vue Test Utils + Jest 为 Vue 组件写单元测试：挂载、断言与异步处理。
date: 2018-10-23 11:00:10
categories: javascript
tags: [vue, test]
---
```

Code blocks name their language, so Rouge can highlight them:

````markdown
```js
const store = new Vuex.Store({ state: { count: 0 } })
```
````

The tokens of a code block are coloured by the design tokens as well, so a
code block follows the appearance of the page.

The categories, the tags and the archive are built from the front matter: a
post belongs to a category and to any number of tags, and the pages under
`article/` list them.

## Feeds

The blog publishes two feeds, both linked from every page:

| URL | Format | Generated by |
| --- | --- | --- |
| `/feed.xml` | RSS 2.0 | `feed.xml` in the repository root |
| `/atom.xml` | Atom 1.0 | [jekyll-feed](https://github.com/jekyll/jekyll-feed) |

`jekyll-feed` is the plugin the Jekyll organisation maintains and it is part of
the `github-pages` gem, so GitHub Pages builds it without a Gemfile. It is
enabled in `_config.yml`:

```yaml
plugins: [jekyll-feed, jekyll-paginate, jekyll-sitemap]

feed:
  path: /atom.xml
  posts_limit: 20
```

`jekyll-sitemap` writes `/sitemap.xml` the same way. The RSS 2.0 feed stays a
template of its own because the Atom feed alone would drop the readers that
still expect `application/rss+xml`; it carries the whole article in
`<content:encoded>` and links with absolute URLs, so a feed reader never has
to follow the redirect from `huihao.github.io` to `bio.wuhh.cc`.

## Reading experience

| Feature | Where | How |
| --- | --- | --- |
| Table of contents | `_includes/toc.html` | built from the `h2` / `h3` of the post, with a scroll spy in `src/js/site.js` |
| Previous / next | `_includes/post-nav.html` | `page.previous` and `page.next` |
| Related posts | `_includes/post-nav.html` | same tag +3, same category +1, the four best matches |
| Social cards | `_includes/head.html` | Open Graph and Twitter tags, the cover image is the first image of the post |
| Structured data | `_includes/head.html` | JSON-LD: `BlogPosting` for a post, `WebSite` with a `SearchAction` for the other pages |
| Search | `search.html` | [Pagefind](https://pagefind.app) indexes the built site |
| Icons | `src/img/*.svg` | `favicon.svg`, `favicon.ico`, `apple-touch-icon.png` and `site.webmanifest` |
| Comments | `_layouts/post.html` | [giscus](https://giscus.app), hidden until it is configured |

### Search

The index is generated by Pagefind from the finished site and committed, the
same way `dist/` is:

```bash
npm run build:search   # jekyll build + pagefind -> pagefind/
```

The page itself is `search.html`; `src/js/search.js` loads
`/pagefind/pagefind.js` on demand, so a visitor only downloads the index when
they actually search. The navigation, the sidebar and the footer are excluded
from the index with `data-pagefind-ignore`, and the list pages are excluded as
well — a search should return articles, not the article list.

### Comments

giscus stores the comments in a GitHub Discussion. Open the repository
settings → Discussions → General and create the discussion category, then fill
the four values from <https://giscus.app> into `_config.yml`:

```yaml
giscus:
  repo: huihao/huihao.github.io
  repo_id: "R_xxxxxxx"
  category: "Comments"
  category_id: "DIC_xxxxxxx"
  client_id: "xxxxx"
```

While `client_id` is empty the comment section is not rendered at all.

## Build

The asset pipeline is plain npm scripts — no gulp, no bower.

```bash
npm install     # install the toolchain
npm run build   # compile src/ -> dist/
npm run dev     # rebuild on change + local server on http://localhost:5050
npm run clean   # remove the generated files in dist/
npm run lint:css   # stylelint over the Sass sources
```

| Script | What it does |
| --- | --- |
| `build:css` | compiles `src/sass/*.scss` into `dist/css/`, then postcss-preset-env + autoprefixer + cssnano |
| `build:css:min` | the same, with cssnano forced on |
| `build:img` | copies `src/img/` into `dist/img/`, re-encoding whatever it can shrink |
| `build:js` | copies `src/js/` into `dist/js/` |
| `build:assets` | renders the icons: `apple-touch-icon.png`, `icon-192.png`, `icon-512.png`, `og-default.png`, `favicon.ico` and `favicon.svg` |
| `build:search` | builds the site with Jekyll and indexes it with Pagefind into `pagefind/` |
| `watch:css` | rebuilds the css whenever `src/sass/` changes |
| `dev:serve` | browser-sync static server on port 5050 |
| `lint:css` | stylelint with `stylelint-config-standard-scss` |
| `site` | `bundle exec jekyll serve --watch`, the Jekyll site itself (needs Ruby) |

The posts are still written with the `Rakefile` helpers (`rake post["Title"]`),
that part has not changed.

`npm run build` has to be run before pushing: `dist/` is committed, the site
loads `/dist/css/main.css` and `/dist/css/markdown.css` straight from the
repository.

## Design system

Everything visual is driven by the custom properties in
`src/sass/_tokens.scss`:

- `--font-text` / `--font-display` / `--font-mono` — the system stack, so
  macOS and iOS render SF Pro and every other platform its closest match.
- `--label`, `--label-secondary`, `--label-tertiary` — the text colours. They
  are opaque enough to clear WCAG AA (4.5:1) on both backgrounds.
- `--background*`, `--fill*`, `--separator`, `--border` — the surfaces.
  `--background-grouped` is the grouped page the list cards float on,
  `--background` the plain page an article is read on.
- `--material` / `--material-thick` / `--glass-filter` — the translucent
  layers and the refraction recipe of a glass surface.
- `--accent` — the cyan the site has always used, tuned per appearance. It is
  a fill, so the text variant is `--accent-text` (deeper in the light
  appearance, so it clears WCAG AA) with `--accent-text-hover` beside it.
- `--measure` — the width of the reading column, 720px.
- `--media-ratio` — the proportions of the artwork of a post.
- `--syntax-*` — the colours of the code blocks, one set per appearance.
- `--space-*`, `--radius-*`, `--duration-*`, `--ease-*` — the 4pt spacing
  grid, the iOS corner radii and the motion.

The dark appearance is a single mixin away; no class is toggled in the markup.
Icons are drawn from a monochrome sprite and inverted automatically when the
page is dark.

### Appearance switch

The site has two appearances, the light one and the dark one, and a switch
between them in the top bar.

- By default the dark appearance follows the system preference, the way a
  native app behaves.
- The switch writes `data-theme="light"` or `data-theme="dark"` on the root
  element and remembers the choice in `localStorage`, so it survives the next
  visit. A visitor who picks light on a dark system keeps the light
  appearance.
- `src/sass/_theme.scss` is the only place that knows how "the page is dark"
  is expressed. The `dark-only` mixin emits the rules twice: once for an
  explicit choice and once for a dark system without a choice, so the same
  markup serves both cases and the page still follows the system when the
  script never runs.
- The choice is applied by a small inline script in `_includes/head.html`,
  before the stylesheet is loaded, so the page never flashes the wrong
  colours.

`src/js/site.js` adds the small pieces a native app has and a blog does not:
the reading progress under the top bar, the copy button on every code block,
the reading time under the title, the back to top button, the appearance
switch, and a fallback for a cover image that does not load. Everything works
without it; the page is the same, only quieter.
